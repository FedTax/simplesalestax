# Whole-plugin Cypress and staging verification implementation plan

Prepared: 2026-10-31. This document is a standalone handoff for a new chat or computer. It replaces the earlier plan in the originating chat. It describes work to implement and execute; it is not a test-results report.

## 1. Goal and agreed decisions

Verify the customer-facing Simple Sales Tax / TaxCloud for WooCommerce experience, the admin settings that control it, and the resulting TaxCloud records. Extend Cypress wherever important behavior lacks repeatable coverage. Identify reproducible defects and report them with evidence. Completion means no unresolved failures in the required coverage, not a guarantee that no undiscovered bugs exist.

- Default WordPress target: `https://woo-staging.do.taxcloud.net/`. Make the target configurable so a later user-specified test site can use the same harness without source edits. TaxCloud dashboard: `https://app.taxcloud.com/`.
- Test the **currently deployed plugin build**. Record its version and, if available, source revision/checksum. Do not deploy this checkout or product fixes as part of the initial verification.
- Use **@Chrome browser tools and the user's existing logged-in Chrome sessions** for WordPress administration, helper installation/setup, exploratory testing, and TaxCloud dashboard verification. Do not require WP/TaxCloud passwords when these sessions work. No SSH/WP-CLI is required. On another computer, the user signs into Chrome first; handle MFA interactively only if a session expires.
- The user has authorized changing WordPress/WooCommerce/TaxCloud plugin settings, adding Cypress tests, and installing a reusable helper plugin through WP admin. The implementer is responsible for completing all setup required for testing; automate it in a one-click helper setup where practical. Still exercise the actual settings screens for settings UI/persistence coverage.
- This is a dedicated test site with no real visitors. **Real WordPress orders and real TaxCloud transaction submissions/captures/imports/refunds are authorized.** Confirm the account/connection identity, record its actual Test/Live status, and test its supported behavior. Do not require Test mode solely because an earlier plan did; do not silently switch TaxCloud account mode or change filing/payout settings. Real orders do not require charging a payment card: use offline payment by default.
- Freely create and **retain** tagged products, variations, categories, pages, coupons, users, orders, and other test fixtures for inspection/reuse. No automatic fixture deletion is required. The helper may remain installed and active or inactive; removal is not an acceptance requirement.
- Preserve the earlier agreement to restore original site/plugin settings after testing, including after failures. Retained fixtures and helper installation are intentional additions and are excluded from settings-restoration equality checks.
- Run remote work sequentially. Settings changes are real and site-wide; concurrent suites or unrelated staging edits must not overlap the run.
- Frontend coverage includes cart, classic checkout, Blocks checkout, My Account, order confirmation/details, and installed integration UIs. Backend/client checks supplement these workflows and must be labeled separately.

## 3. Current implementation and required test architecture

The current checkout has these useful foundations:

- `npm run test:e2e` runs local Docker plugin workflows with controlled TaxCloud responses. `-- --live` calls real TaxCloud services with both credential profiles, but the helper forces API setting V3.
- The documented baseline is 28 fixture tests and 15 live tests; these are reference counts, not acceptance targets for the expanded suite. Existing Blocks checks cover rendering/totals, not order placement.
- The default admin suite assumes local login, seeded product names, and fixed cart/checkout page IDs. It cannot safely be pointed at staging unchanged.
- PHP regressions and Cypress contracts cover API routing, exemptions, local pickup, refunds, and V3 clients. The existing `staging` runner is a direct legacy TaxCloud API suite, **not** a test of the WooCommerce staging website.

Extend `cypress/run.js` and `cypress/suites.js` with a distinct `staging-site` suite. Preserve existing suite meanings and local-only/CI protections. Add these commands:

```sh
# New commands to implement; not available merely by following this document.
npm run test:staging:preflight
npm run test:staging:setup
npm run test:staging
npm run test:staging:open
npm run test:staging:restore -- --run-id=RUN_ID
# Example for a replacement target explicitly supplied by the user:
npm run test:staging -- --target-url=https://USER_SPECIFIED_TEST_SITE/
```

Preflight inspects the target without setup mutations. Setup opens or resumes the helper's one-click workflow using @Chrome; the main command ensures setup is complete and runs the matrix below. Restore recovers a specific interrupted run and restores settings without deleting retained test data or uninstalling the helper. These commands that use @Chrome require execution by an agent with the browser tools; do not present them as a way for plain Node to attach to the user's Chrome session automatically. Implement a pause/resume checkpoint for the Chrome setup step and document that dependency.

Store the default URL in non-secret target configuration, allow an explicit `--target-url` override, and normalize the resulting HTTPS base URL. Pin all mutations and authenticated requests to the selected origin; reject cross-origin redirects and accidental fallback to localhost. If the installation uses a URL subdirectory, preserve that base path when constructing WP/admin/REST URLs. On a later user-directed target change, rerun site/version/access discovery and setup; do not reuse old site IDs, sessions, tokens, snapshots, locks, or remote record assumptions. Key manifests, access material, result directories and locks by target identity plus run ID. Acquire a run lock before changing settings, with explicit interrupted-run recovery rather than automatic takeover. Disable automatic test retries for remote transaction workflows. Do not hardcode an allowlist that prevents a future user-authorized target change.

Extract reusable browser actions/assertions from the current specs, retaining local fixture behavior. Split new specs by settings/products, shopping/totals, exemptions, order lifecycle, and frontend presentation. Each independent scenario creates its own required state; avoid depending on an unrelated previous `it` to have created a cart/order/certificate. Share a resource manifest and configuration scheduler across specs, not hidden test dependencies.

### Reusable helper and one-click setup

Package a **normal WordPress plugin**, upload/activate it through admin using @Chrome, and add an administrator-only **Prepare test site** action. It may remain installed and active or inactive afterward. Do not attempt the local MU-plugin/Docker installation mechanism remotely. Its fixed authenticated controls support setup preview/apply, run start/status, fixture creation, order/package reads, sanitized evidence reads, settings restoration, and interrupted-run recovery.

The setup action takes a run/configuration profile, snapshots settings before its first write, provisions the runner/customer/product/page/shipping fixtures, enables an offline gateway, assigns classic/Blocks pages, configures WooCommerce taxes and the plugin's required options, and checks required compiled frontend assets. Use the supplied API pair and origins fetched from that actual connection. Resolve derived integration mode through the plugin's real verification flow. Use existing WordPress/WooCommerce/plugin APIs to **persist real settings**, not runtime overrides. Allowlist the supported setup fields; do not expose a general option-write endpoint. Show a sanitized setup summary and return ready/blocked with actionable errors. Re-running setup resumes/reuses tagged resources rather than creating duplicates; original settings snapshots must not be overwritten by the already-modified setup state. If the deployed plugin/assets cannot support a required feature, report it rather than deploying product changes automatically.

Known setup behavior reported by the user: saving new API credentials can clear **Shipping Origin Addresses**. After every credential change, including helper-driven setup, fetch the new connection's available origins, explicitly select the first available selectable address, and save again as a separate step. Reload and verify that selection persisted before declaring setup ready. A placeholder/empty/disabled option is not an address; if no selectable address exists, report setup as blocked rather than continuing with an empty origin.

- Require WP admin capability plus normal cookie authentication/REST nonces. Reject anonymous/customer requests, mismatched run IDs, and access to objects not owned by the run. Do not add arbitrary PHP execution, arbitrary file reads, or a general option-write endpoint.
- Create uniquely tagged users, products/variations/categories, coupons, classic/Blocks pages, shipping fixtures, and test-only fee scenarios. Keep a manifest of all created IDs, configuration checkpoints, remote records, and restoration status. Keep fixtures afterward and make subsequent setup runs safe to reuse them; transaction scenarios still need fresh order/cart identifiers.
- Scope supporting hooks such as test-email suppression and synthetic fees to run-owned customer/session/order records. Use a run marker for guest sessions. Use cheque/offline payment; never charge a real gateway.
- Read genuine saved TaxCloud settings. The helper may save prerequisite settings during one-click setup, but **must not override their values at runtime, replace live API outcomes, or fake the derived connection mode**. For each matrix group, save credentials/API selection and verify persistence through the settings UI; test relevant settings controls there as well. Helper setup alone is not evidence that the UI works.
- Do not globally disable Store API nonce checks as the local helper does. Use real nonce/cart-token flows.
- Use WordPress/WooCommerce APIs compatible with the active order storage mode. Discover HPOS versus legacy order editor URLs rather than assuming `post.php` works.
- Observe V3 HTTP responses without replacing them. V1 normally uses native cURL and bypasses WordPress HTTP hooks: collect V1 evidence from the deployed plugin's existing logs, order metadata, and dashboard records. The existing V1 header filter can count attempted endpoint calls, but must not be represented as response evidence. Do not patch the deployed vendor client or force a different transport to manufacture evidence parity.
- Report any V1 response-level observation gap precisely; UI success alone is insufficient proof of remote capture/refund.

Validate helper authentication, ownership restrictions, setup/restoration idempotence, and the failure path before installing it on the target. When a run ends, mark it inactive and leave the helper inert for ordinary requests, even if the plugin remains active.
